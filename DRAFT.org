#+begin_quote
*NOTE:* This document outlines the language's design, feature sets,
trade offs, soundness and related aspects. It aims to provide a
detailed and unambiguous reference. It is an ongoing process, and
nothing is finalized.
#+end_quote

Miru is a strictly evaluated functional language from the ML family
that uses S-expressions for its primary syntax. It aims to compose
bleeding edge computer science research like effects handlers,
co-effects, ordered modalities, first-class modules, liquid refinement
types, and others orthogonally. It is designed to be maximally
pragmatic and useful for general purpose computing while retaining the
necessary features to function as a strong scientific language.

* 1. Starting out with comments

The easiest way to comment is by prefixing a phrase with ~;~. The number
of ~;~ characters that follow changes the semantic meaning of the
comment.

#+begin_src clojure
; This comment is used for inline or internal notes.
;; This comment used for standalone lines.

;;; This comment is used for documentation. It is placed on top of
;;; expressions or declarations.

#! Hashbangs are also treated as comments. They are semantically the
#! same as `;;`.
#+end_src

Miru has various built-in reader macros. One of them is the discard
reader macro ~#_~. It discards any form that immediately follows it,
essentially turning the form into an inplace comment. An indentation
delimiter between the reader macro and the form is mandatory when the
first token of the form is a valid identifier.

#+begin_src clojure
(+ 1 #_ 2 3) ; (+ 1 3)

(+ 1 #_2 3)
;;   ^^^ ERROR: Unbounded reader macro `_2`.

(+ 1 #_(+ 1 1) 3) ; (+ 1 3)
                  ; It works because `(` is not a valid identifier.
#+end_src

To note, reader macros are not user extensible. Extensible reader
macros are an evergreen minefield of broken tooling that Miru aims to
avoid. We'll look into safer alternatives down the line.

* 2. Within bindings

** 2.1. Named and function bindings

Bindings use the ~val~-form. This includes nullary (arity = 0) named
bindings and fixed-arity (arity >= 1) function bindings. They are
immutable and sequential.

#+begin_src clojure
(val name "Miru") ; This is a named binding.

;; This is a unary function binding. Arguments are passed in tuple
;; form [<x> <y> ...].
(val greet [name]
  (String/concat " " '("Hello" name))) ; '(...) is a list at all
                                       ; times, never a quotation.

;; Now, we can apply the function.
(greet name) ; Hello Miru
#+end_src

In this example, ~String~ is a module, ~/~ is the universal inspection
operator, and ~concat~ is a binary function defined inside the ~String~
module. Note that all bindings and types in Miru follow the ~kebab-case~
convention; the only exceptions include modules and type constructors
which use ~Header-kebab-case~.

Bindings being sequential make shadowing an intrinsic property. In
fact, a binding of arbitrary arity can be shadowed by another binding
of the same name, regardless of its arity.

#+begin_src clojure
(val x 10)

;; Evaluates `x` to 10 and rebinds it to 30, shadowing the previous
;; `x`.
(val x (+ x 20))

;; Shadows `x` with a new function binding. A function binding is just
;; a lambda bound to a named binding.
(val x [y z]
  ; `x` inside the body refers to the outer named binding returning
  ; `30`. Functions are non-recursive by default to preserve the
  ; sequential semantics; if `x` wasn't defined in the immediate
  ; parent scope, this would fail to compile.
  (+ x (* y z))) 

;; Basic function application.
(x 2 3) ; 36

;; Evaluates `x` and rebinds the value to the same name. This is not a
;; recursive call.
(val x (x 2 3))
#+end_src

** 2.2. Sequential scopes, threading and parallel bindings

~val~-form is sequential but requires an existing scope to bind to. In
such cases, we can use the ~begin~-form to introduce a fresh top-down
sequential scope.

#+begin_src clojure
(begin
  (val x 10)
  (val y 11)
  (+ x y)) ; 21
#+end_src

Threading is performed using the ~do~-form. It is strictly thread-last
i.e. the value to be threaded is applied as the last argument of each
partial application.

#+begin_src clojure
(do
  (..= 1 6) ; An inclusive range.
  (filter odd?)
  (foldr + 0)) ; 9
#+end_src

Parallel bindings can be introduced using two ways:
+ Product unpacking
+ ~and~-form

Miru only allows us to unpack product types i.e. tuples and records
using the ~val~-form because they can be unpacked using a single
exhaustive pattern. This doesn't hold true for sum types or arbitrary
data structures like lists or arrays; the ~match~-form is a better fit
for those use-cases.

#+begin_src clojure
;; `a` and `b` are evaluated in parallel.
(let [a b] [1.0 "Hello, World!"])
#+end_src

~and~-form allows us to introduce multiple distinct bindings
simultaneously. All expressions in a binding chain are evaluated in
parallel within the parent scope before any new symbols are bound.

#+begin_src clojure
;; These expressions are evaluated parallely in the parent scope; `x`
;; can't query it's environment to read the value of `y`.
(val y 39)
(and x (+ y 1))
;;        ^ ERROR: Unbound binding `y`.
#+end_src

This makes `and`-form great for handling mutual recursion. When
function bindings are chained using the `and`-form, they share a
mutual scope, allowing them to freely reference one another regardless
of their lexical ordering. Let's take a brief look at recursion in the
next section.

** 2.3. Recursion

Recursive functions must be marked with the ~rec~ keyword. Let's start
with a tail-recursive implementation of factorial. Miru will perform
tail-call elimination for all tail-recursive functions.

#+begin_src clojure
(val rec factorial [n acc]
  (if (<= n 1)
    acc
    (factorial (- n 1) (* n acc))))

(factorial 6 1) ; 720
#+end_src

If we try to do the same but without the ~rec~ keyword, we are greeted
with an error.

#+begin_src clojure
(val factorial [n acc]
  (if (<= n 1)
    acc
    (factorial (- n 1) (* n acc))))
;;  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ ERROR: Unbound binding `factorial`.
;;                                 Did you mean to mark `factorial` as
;;                                 recursive?
;;
;;                                 1 |(val rec factorial [n acc]
;;                                         ++++         +
#+end_src

We can extend this naturally to mutually recursive functions.

#+begin_src clojure
(val rec even? [n] ; Boolean functions end in `?` as convention.
  (match n
    0 true
    n (odd? (- n 1))))

(and odd? [n]
  (match n
    0 false
    n (even? (- n 1))))
#+end_src

An entire sequence of ~val~ and ~and~-forms must either be entirely
mutually recursive or non-recursive. We can't mix both behaviors
within the same chain.

Miru supports fixed-point recursion using ~Function/fix~, allowing us to
bypass explicit recursion specifiers entirely. Any function definition
can be treated as a fixed point by mapping it to a core combinator.

Below, we reimplement the factorial function using this fixed-point
style, the ~fun~-form, and the ~#(...)~ reader macro for ~fun~-forms.

#+begin_src clojure 
(val factorial (Function/fix
  ; `%` denotes the first argument. `%n` denotes the nth
  ; argument.
  #(if (<= %2 1)
     acc
     (% (- %2 1) (* %2 %3))))))
#+end_src

This can also be written using the plain old ~fun~-form.

#+begin_src clojure
(val factorial (Function/fix
  (fun [self n acc]
    (if (<= n 1)
      acc
      (self (- n 1) (* n acc)))))))
#+end_src

Fix-points aren't limited to functions; we can also find fix-points of
data types. We'll explore them and their orthogonal variants in later
chapters.

** 2.4. Automatic currying

Miru supports automatic currying. Consequently, variadic arguments,
named arguments, and default arguments are not supported due to their
structural incompatibility and awkwardness.

The need for named arguments is entirely replaced by utilizing (stack
allocated) structural records instead. Similarly, default arguments
can be replaced by composing functions returning a default record
value with functional update. We'll learn more about them in later
chapters.

#+begin_src clojure
(val multiply [a b]
  (* a b))

(val multiply-by-5 (multiply 5)) ; It wraps a lambda that expects the
                                 ; remaining arguments.
                                 
(multiply-by-5 10) ; 50
#+end_src

Currying makes composition clean and natural. In this example, `(* 2)`
wraps a lambda that expects a second argument.

#+begin_src clojure
(val new-list (List/map (* 2) '(1 2 3 4))) ; '(2 4 6 8)
#+end_src

** 2.5. Type annotations

Let's get back to the ~greet~ function, which is inferred as ~string ->
string~. We can also use the ~val~-annotation form to define the type
of a binding ourselves.

#+begin_src clojure
(val greet : string -> string) ; `greet` is the name of the binding.
                               ; The name is separated from the
                               ; signature using the type marker
                               ; `:`. `->` is a mapping; it takes a
                               ; string as input and maps it to
                               ; another string as output.
#+end_src

Let's annotate the ~multiply~ function we made use of in the currying
example.

#+begin_src clojure
(val multiply : int -> int -> int) ; The signature is curried. The
                                   ; last type in the chain is the
                                   ; return type of the entire
                                   ; expression.
(val multiply [a b]
  (* a b)) ; The result of the last expression is automatically
           ; returned from this scope. No return keyword required.
#+end_src

We can partially annotate fields we care about while leaving the
others for the compiler to infer using type holes ~_~.

#+begin_src clojure
(val multiply : _ -> _ -> int)
(val multiply [a b]
  (* a b))
#+end_src

Type holes are not just limited to types, they can also be used as
placeholders for effects, contexts, modalities and refinement
predicates. Any unannotated component acts as an implicit type hole,
allowing us to specify only the exact constraints we care about at any
given time.

We can annotate inline parameters and expressions with types
by reusing the exact same ~val~-annotation format we use at the top
level.

#+begin_src clojure 
(val multiply [(val a : int) b]
;;             ^^^^^^^^^^^^^ example of an annotation.
  (val (* a b) : int))
;;     ^^^^^^^ expressions are also allowed.
#+end_src

There is no separate type marker for returning value; we annotate the
final returning expression directly. This is semantically the same as:

#+begin_src clojure
(val multiply : int -> _ -> int)
(val multiply [a b]
  (* a b))
#+end_src

#+begin_quote
*NOTE:* While inline expressions offer a flexible way to guide the
compiler locally, they should be used sparingly. Whenever a function
signature becomes complex, involving dense modal logic, effects, or
refinements, the top-level ~val~-annotation form is preferred to keep
things readable.
#+end_quote

** 2.6. Calling a function just for its value and/or side-effects

As stated before, function bindings must have arity >= 1. Some
functions naturally don't take any arguments, so we use the `unit`
type for the first argument, effectively calling the function only for
its value and/or side-effects.

#+begin_src clojure
(val hello-world : unit -> string)
;;                 ^^^^ is the unit type.
(val hello-world [()]
;;                ^^ is the unit value.
  "Hello, World!")

;; This is how we'd call the function.
(hello-world ())
#+end_src

We'll look into how Miru tracks side-effects in its type system in
later chapters.

** 2.7. Lambdas and aliasing

We can define functions using lambdas and named bindings.

#+begin_src clojure
(val square (fun [x] (* x x)))

;; Or, we could always use the reader form.
(val square #(* % %))

(square 6) ; 36
#+end_src

If we want to alias a function, we simply do:

#+begin_src clojure
(val aliased-square square)
#+end_src

** 2.8. Symbolic functions

Symbolic functions are valid, but they must be defined inside an
enclosure ~(...)~.

#+begin_src clojure
(val (~/) [x] (/ 1.0 x))

(~/ 4.0) ; 0.25
#+end_src

* 3. Within strings

** 3.1. Standard strings

Before we start printing values, we need to explore strings and their
forms. We start with standard strings and the ability to tag them. In
this example, ~#"~ always closes with ~"#~. Tags can also be named using
~#<name>"~ and ~"<name>#~ pairs.

#+begin_src clojure
(val str "I'm a normal string")

(val str #"I'm a tagged string with no name"#)

(val str #tag"I'm a tagged string with a name"tag#)
#+end_src

** 3.2. Raw strings

Raw strings are fully supported.

#+begin_src clojure
(val str r"I'm a raw string\n")

(val str r#"I can also be tagged\n"#)
#+end_src

** 3.3. Format strings/constructors

Format strings are special because they aren't actually strings at
all. They allow interpolation and are desugared into generalized
variant constructors, much like in OCaml. They retain the "string"
designation purely for convenience and similarity, though calling them
format constructors is more precise. By default, interpolation uses
~{...}~ and lets us embed named bindings directly.

#+begin_src clojure
(val d "interpolate")

(val d f"I can {d} values!") ; I can interpolate values!
#+end_src

Alternatively, we can also utilize the constructor form. Note that we
can't mix the literal and constructor forms together. We will dive
deeper into algebraic data types later.

#+begin_src clojure
(val d (f"I can {} values!" d))
#+end_src

** 3.4. Chaining and interpolation

Format constructors also support chaining, which alter the
interpolation semantics accordingly.

#+begin_src clojure
(val d ff"I can {{d}} values!") ; `ff` shifts the interpolation target
                                ; from {...} to {{...}}.
#+end_src

The rule of thumb follows a predictable pattern: ~f -> {...}~, ~ff ->
{{...}}~, ~fff -> {{{...}}}~, or more generally, ~f_n -> {_n ... }_n~.

Raw format constructors are available and support chaining as well.

#+begin_src clojure
(val d (rff"I can {{}} values and raw literals like \n" d))
#+end_src

** 3.5. Printing with format constructors

Now, we've everything required to start printing values. Let's
reimplement the ~greet~ function to print the value directly rather
than returning a string.

#+begin_src clojure
(val greet [name]
  ; `<>` is a semigroup append function. Since string concatenation
  ; forms a free semigroup, it performs a string concatenation.
  (println (f"{}" (<> "Hello, " name))))
#+end_src

~println~ always expects a format constructor; we can't pass a
standard string as its argument directly. To convert format strings
into plain strings, we can use the ~String/from-format~ function.

#+begin_src clojure
(val to-embed "World")
(String/from-format f"Hello, {to-embed}!") ; Hello, World!
#+end_src

* 4. Brief view of data-structures

** 4.1. Lists

Lists are dynamic, ordered, homogeneous singly-linked lists. Lists are
persistent data structures; it is immutable and relies on structural
sharing to make copying efficient.

#+begin_src clojure
(val lst '(1 2 3))
#+end_src

Lists and singly linked lists; they do not provide language syntax for
random access. However, we can use the ~List/nth~ function to walk the
list and access specific values at the cost of indirection. ~List/nth~
returns a ~option~ constructor.

#+begin_src clojure
(println (f"{}" (List/nth 1 lst))) ; (Some 2)
#+end_src

Lists are intertwined with the cons function ~::~. The following
declaration is semantically identical to the first:

#+begin_src clojure
(val lst (:: 1 (:: 2 (:: 3 '()))))
#+end_src

We can always prepend more elements structurally.

#+begin_src clojure
(val lst-new (:: 0 lst))
#+end_src

We can also use the ~match~-form to deconstruct lists. We'll look more
into ~match~-forms when we introduce variant constructors.

#+begin_src clojure
(match lst
  '()         (println f"The list is empty")
  (:: head _) (println f"The first element is {head}"))
;;         ^ we discard the tail here.
#+end_src

** 4.2. Arrays

Arrays are fixed-sized, contiguous, homogeneous collections. Unlike in
OCaml, Miru arrays are immutable.

#+begin_src clojure
(val arr [| 1 2 3 |])
#+end_src

Arrays fields can be accessed by their index using field inspection
reader ~/[...]~ starting at ~0~.

#+begin_src clojure
(println (f"{}" arr/[2])) ; 3
#+end_src

Miru arrays are ~N~-dimensional and column-major. They are stored
contiguously in memory, and require precise offset calculations to
access elements. The field inspection reader ~/[...]~ validates direct
indexes, but can't validate indirect indexes. When indexing fails, an
effect is performed and reflected in the effect row. Converting these
effects to an optional is justified in many cases. This can be done
using ~Array/optify~ which intercepts such effects and returns an
~option~.

#+begin_src clojure
(println (f"{}" (Array/optify arr/[2]))) ; (Some 3)
(println (f"{}" (Array/optify arr/[6]))) ; (None)
#+end_src

Let's take a deeper look into how ~N~-dimensional arrays are written.

#+begin_src clojure
(val arr [| 1 4 7 |   ; Pipes are used to segment dimensions.
            2 5 8 |   ; Dimension = (no. of pipes) + 1.
            3 6 9 |])

(println (f"{}" arr/[2 1])) ; 8
;;                  ^^^^^ is [column row]
#+end_src

We can also access elements by offsets using ~Array/nth-offset~,
returning an ~option~. In this example, the offset must be a
pre-calculated using the formula ~offset = (column * height) + row~
which equates to ~7~.

#+begin_src clojure
(println (f"{}" (Array/nth-offset 8 arr))) ; (Some 9)
#+end_src

The aforementioned formula is only valid for 2D-arrays. Because offset
calculation is extremely common, we can use ~Array/offset~ going
forward.

#+begin_src clojure
(println (f"{}" (Array/nth-offset (Array/offset '(2 1)) arr)))
;;      Dimensions are represented using a list ^^^^^^
#+end_src

** 4.3. Mutable arrays

Mutable arrays are the mutable variant of arrays, allowing for
in-place mutation. In Miru, mutability is a (tracked) property of data
structures. Consequently, Miru has no concept of a mutable pointer,
though we will emulate one later. We'll also look into mutability
tracking in later chapters. For now, let's ignore the handling
semantics and explore the properties of mutable arrays.

#+begin_src clojure
(val arr [! 1 2 3 !])

;; We can use the same `/[...]` operator.
(println (f"{}" arr/[2])) ; 3

;; `Array/nth-offset` works for both `Array` and `Mut-array` using
;; contextual implicits. We'll look into them later.
(println (f"{}" (Array/nth-offset 1 arr))) ; (Some 2)
#+end_src

Miru provides a universal mutating primitive ~<-~, that can be used to
mutate specific fields of mutable data structures in-place.

#+begin_src clojure
(<- arr/[2] 4)
(println (f"{}" arr/[2])) ; 4
#+end_src

Mutable arrays can also be ~N~-dimensional but their shape is fixed.

#+begin_src clojure
(val arr [! 1 4 7 |
            2 5 8 |
            3 6 9 !])

(println (f"{}" arr/[2 1])) ; 8

(<- arr/[2 1] 10)

;; There is no separate `Mut-array/offset` either.
(println (f"{}" (Array/nth-offset (Array/offset '(2 1)) arr)))
#+end_src

** 4.4. Dynamic arrays

Dynamic arrays are the resizable variant of mutable arrays, commonly
referred to as vectors in other languages. Unlike their fixed-size
counterparts, dynamic arrays are strictly ~1~-dimensional. Hence, there
is no intrinsic way to build dynamically dimension-reshaping
arrays.

Instead, we can use a dynamic array to handle runtime growth and
perform a zero-copy cast to a fixed N-D array, provided the total
element count matches the target shape at runtime. This operation is
inherently effectful given its fallible nature.

The mutability of dynamic arrays is also tracked similar to mutable
arrays or any data-structure with interior mutability. For now, let's
ignore the handling semantics and explore the properties of dynamic
arrays.

#+begin_src clojure
(val dyn-arr [~ 1 2 3 4 5 6 7 8 9 ~])

(println (f"{}" dyn-arr/[5])) ; 6

;; Push a new element to the dynamic array. Functions ending in `!`
;; are in-place mutating by convention.
(Dyn-array/push! 10 dyn-arr)

;; Pop elements as needed.
(Dyn-array/pop! dyn-arr)

;; No `nth-offset` here because dynamic arrays are always 1D.
(println (f"{}" (Dyn-array/nth 8 dyn-arr))) ; (Some 9)

(val arr (Array/from-dyn '(3 3) dyn-arr)) ; Zero-copy cast.
#+end_src

Non-owning or borrowed views are as important as owning data

operations using strided subsections. Let's explore the three view
types Miru provides: ~string-view~, ~array-view~ and ~mut-array-view~ and
their respective modules. Views are deeply intertwined with modalities
(an implementation of structural co-effects) and borrowing, which we
will explore in further detail later.

** 4.6. Sets

Base provides five set variants: CHAMP sets, hash sets, sorted sets,
ordered sets, and bit sets. Let's take a brief look at them all at
once.

#+begin_src clojure
;; CHAMP sets are the default set implementation in Miru. They are
;; immutable, persistent, purely applicative, unordered, homogeneous
;; collections that enforce unique elements.
(Set/from-list '(1 2 3))
;; or the alias:
(Champ-set/from-list '(1 2 3))

;; Hashsets are mutable, non-persistent, unordered (hash-based) linear
;; collections.
(Base/Containers/Hash-set/from-list '(1 2 3))

;; Sorted sets are immutable, persistent, value-ordered (Persistent
;; B-Tree) collections.
(Base/Containers/Sorted-set/from-list '(1 2 3))
;; or the alias:
(Base/Containers/B-tree-set/from-list '(1 2 3))

;; Ordered sets are immutable, persistent, insertion-ordered (Linked
;; CHAMP) collections.
(Base/Containers/Ordered-set/from-list '(1 2 3))
;; or the alias:
(Base/Containers/Linked-champ-set/from-list '(1 2 3))

;; Bit sets are mutable or unboxed, bitwise-packed sets of
;; non-negative integers.
(Base/Containers/Bit-set/from-list '(0 1 1 0))
#+end_src

** 4.7. Maps

Base provides four map variants: CHAMP maps, hash maps, sorted maps,
and ordered maps. Let's take a brief look at them all at once.

#+begin_src clojure
;; CHAMP maps are the default map implementation in Miru. They are
;; immutable, persistent, purely applicative, unordered, homogeneous
;; key-value collections.
(Map/from-list '(["id" 1] ["id-2" 2])) ; List of 2-tuple (pair).
;; or the alias:
(Champ-map/from-list '(["id" 1] ["id-2" 2]))

;; Hashmaps are mutable, non-persistent, unordered (hash-based) linear
;; key-value maps.
(Base/Containers/Hash-map/from-list '(["id" 1] ["id-2" 2]))

;; Sorted maps are immutable, persistent, value-ordered (Persistent
;; B-Tree) key-value maps. Orders entries by key comparison to enable
;; range queries and bounds slicing.
(Base/Containers/Sorted-map/from-list '(["id" 1] ["id-2" 2]))
;; or the alias:
(Base/Containers/B-tree-map/from-list '(["id" 1] ["id-2" 2]))

;; Ordered maps are immutable, persistent, insertion-ordered (Linked
;; CHAMP) key-value maps.
(Base/Containers/Ordered-map/from-list '(["id" 1] ["id-2" 2]))
;; or the alias:
(Base/Containers/Linked-champ-map/from-list '(["id" 1] ["id-2" 2]))
#+end_src

Mutable hash sets and hash maps can function as accumulators for the
persistent variants, much like dynamic arrays do for N-D
arrays. However, unlike the latter, converting between hash variants
and persistent variants is not zero-copy and will allocate due to
layout differences.
